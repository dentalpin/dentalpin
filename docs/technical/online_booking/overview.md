# Online booking backend

The optional `online_booking` module is disabled by default. Configure an HTTPS confirmation-page URL, a clinic professional and booking bounds through the authenticated settings endpoint. Public availability and request routes are under `/api/v1/online_booking/public/{clinic_id}`; staff settings and decision routes require authenticated, scoped permissions. The reception accept action uses the solid primary button style and is enabled only for confirmed requests when the user has the required permissions. The inbox returns pages of 50 live requests and excludes expired holds without waiting for the cleanup job. Reception selects an active clinic professional, optional active cabinet and duration; nullable `first_visit_minutes` and `checkup_minutes` settings default each reason to `slot_minutes` when absent. The selected duration is checked under the booking lock against the chosen professional's and cabinet's active appointments and the chosen professional's other live holds. The navigation count includes only confirmed requests whose start is in the future and requires `online_booking.read`. Put only the required public paths and methods behind a TLS reverse proxy; keep staff paths, other modules, documentation and the database private. Trust forwarded addresses only from configured proxies.

Pending requests hold for 10 minutes; confirmation consumes a hashed single-use token. Confirmed requests hold until a decision or the start time. A 15-minute job expires stale requests, deletes rejected/expired requests after 30 days and erases contact information on accepted requests after 90 days. Cleanup depends on the scheduler running. Confirmation and rejection emails are queued with `NotificationGateway.enqueue` (types `booking_confirmation` and `booking_rejection`, email channel, `force_send`) inside the request transaction, so a rolled-back request queues nothing; the notifications outbox delivers them after commit with its usual retry. System templates are seeded for es and en by migration `ob_0003`; the other ten locales hold English copy until translated, and clinics can override any template. A confirmation still queued when its request is no longer pending is cancelled by the cleanup job. Delivery uses whatever email provider the clinic configured in notifications. Because the confirmation link is part of the queued message context until it is sent, treat the communication log as sensitive. A separate confirmation page must read the URL fragment and submit the token; a link fetch alone must not confirm.

Agenda and online booking acquire the same transaction-scoped clinic lock. Availability is that of the professional configured in the settings: the `schedules` module supplies their hours, and only their active appointments and live holds block a slot; other professionals' appointments do not. Each request stores that professional. Creating and confirming a request recheck that professional's appointments and live holds under that lock; accepting rechecks the professional and cabinet reception chose (an appointment with the same professional or the same cabinet blocks). Agenda serializes writes but intentionally does not reject overlapping appointments; an agenda write after a booking decision can still introduce a conflict. See [issue #905](https://github.com/dentalpin/dentalpin/issues/905) and [#937](https://github.com/dentalpin/dentalpin/pull/937). Request-IP, availability-IP and contact limits use hashed, short-lived PostgreSQL counters shared between workers. A second existing IP limiter is process-local. Protect the perimeter as well and trust forwarded client addresses only from configured proxies. This phase books for one configured professional per clinic.

The standalone static `public_widget/` supports Spanish and English and uses same-origin, cookie-free API calls. Its committed configuration is intentionally disabled until a clinic UUID and HTTPS privacy URL are supplied. `GET /public/{clinic_id}/challenge` issues a clinic-bound ALTCHA v2 proof of work; `POST /public/{clinic_id}/requests` requires its solution. The verifier checks expiration and signature and atomically consumes the proof in the booking transaction, preventing replay after a successful commit. See the widget README for reproducible build, iframe CSP and the exact five public methods and routes.
