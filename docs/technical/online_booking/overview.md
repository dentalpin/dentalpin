# Online booking backend

The optional `online_booking` module is disabled by default. Configure an HTTPS confirmation-page URL, a clinic professional and booking bounds through the authenticated settings endpoint. Public availability and request routes are under `/api/v1/online_booking/public/{clinic_id}`; staff settings and decision routes require authenticated, scoped permissions. The reception accept action uses the solid primary button style and is enabled only for confirmed requests when the user has the required permissions. The inbox returns pages of 50 live requests and excludes expired holds without waiting for the cleanup job. Reception selects an active clinic professional, optional active cabinet and duration; nullable `first_visit_minutes` and `checkup_minutes` settings default each reason to `slot_minutes` when absent. The selected duration is checked under the booking lock against the chosen professional's and cabinet's active appointments and the chosen professional's other live holds. The navigation count includes only confirmed requests whose start is in the future and requires `online_booking.read`. Put only the required public paths and methods behind a TLS reverse proxy; keep staff paths, other modules, documentation and the database private. Trust forwarded addresses only from configured proxies.

Pending requests hold for 10 minutes; confirmation consumes a hashed single-use token. Confirmed requests hold until a decision or the start time. A 15-minute job expires stale requests, deletes rejected/expired requests after 30 days and erases contact information on accepted requests after 90 days. Cleanup depends on the scheduler running. Confirmation and rejection emails are queued with `NotificationGateway.enqueue` (types `booking_confirmation` and `booking_rejection`, email channel, `force_send`) inside the request transaction, so a rolled-back request queues nothing; the notifications outbox delivers them after commit with its usual retry. Both render in the `language` the visitor sent with the request (stored on the request since migration `ob_0005`); a request without it (sent without a language, or made before `ob_0005`) uses the clinic's communication language. System templates are seeded for es and en by migration `ob_0003`; the other ten locales hold English copy until translated, and clinics can override any template. A confirmation still queued when its request is no longer pending is cancelled by the cleanup job. Delivery uses whatever email provider the clinic configured in notifications. Because the confirmation link is part of the queued message context until it is sent, treat the communication log as sensitive. A separate confirmation page must read the URL fragment and submit the token; a link fetch alone must not confirm.

Agenda and online booking acquire the same transaction-scoped clinic lock. Availability is that of the professional configured in the settings: the `schedules` module supplies their hours, and only their active appointments and live holds block a slot; other professionals' appointments do not. Each request stores that professional. The public routes answer 404 (booking unavailable) unless that professional is an active user with a professional membership in the clinic, and the reservation rechecks this under the lock; enabling the settings for an inactive user is rejected ([#1100](https://github.com/dentalpin/dentalpin/issues/1100)). The membership check applies only when enabling: a disabled configuration can always be saved, and a professional id that is not a professional member of the clinic (removed, or another clinic's user) is then stored as NULL ([#1149](https://github.com/dentalpin/dentalpin/issues/1149)). Creating and confirming a request recheck that professional's appointments and live holds under that lock; accepting rechecks the professional and cabinet reception chose (an appointment with the same professional or the same cabinet blocks). Agenda serializes writes but intentionally does not reject overlapping appointments; an agenda write after a booking decision can still introduce a conflict. See [issue #905](https://github.com/dentalpin/dentalpin/issues/905) and [#937](https://github.com/dentalpin/dentalpin/pull/937). Request-IP, availability-IP and contact limits use hashed, short-lived PostgreSQL counters shared between workers. A second existing IP limiter is process-local. Protect the perimeter as well and trust forwarded client addresses only from configured proxies. This phase books for one configured professional per clinic.

The public page is a Nuxt page of the module's layer, `/p/booking/{clinicId}` (`frontend/pages/p/booking/[clinicId].vue`), built like the other public screens (`/p/budget`, `/p/check-in`, `/p/consent`, `/p/push`): `public` layout without the DentalPin header, no authentication (`/p/booking` is in the public route list of `auth.global.ts`) and cookie-free, same-origin calls (`credentials: 'omit'`, no referrer) to the public API through `usePublicBooking`. It has the twelve application locales (the language is switched in memory only; the request `language` is `es` for Spanish and `en` otherwise because email templates exist in those two). The confirmation token arrives in the URL fragment (`#token=`), is removed from the address bar on load and is sent only by the visitor's explicit POST. `GET /public/{clinic_id}/challenge` issues a clinic-bound ALTCHA v2 proof of work, solved by the `altcha` widget (loaded client-side only); `POST /public/{clinic_id}/requests` requires its solution. The verifier checks expiration and signature and atomically consumes the proof in the booking transaction, preventing replay after a successful commit; a rejected proof raises `CaptchaInvalidError` (400) and a replayed one `CaptchaReusedError` (409), mapped to HTTP by `BookingRoute` like every other `BookingError`.

Public config also returns `privacy_url` (required for the form to be sendable) and `embed_origins`. **Embedding:** the page can be framed from the clinic's website. `embed_origins` is a list of at most ten HTTPS origins (no path, query or credentials), configured in the settings. Nitro (`frontend/server/middleware/booking-embed.ts`, `server/utils/bookingEmbed.ts`) reads them from the public config endpoint (cached 60 s, fail closed to `'self'`, skipped for top-level navigations) and sends `Content-Security-Policy: frame-ancestors 'self' <origins>` for `/p/booking/{clinicId}` only; `csp.ts` reuses the value in `enforce` mode. The Caddyfile omits its own `frame-ancestors 'self'` on `/p/booking/*`; another reverse proxy must do the same. See `docs/technical/security-csp.md`. Set the settings' `public_url` to the DentalPin page address, not to the page that embeds it: the confirmation fragment would never reach the iframe.

**Perimeter for an internet-facing booking page only:** expose `GET /p/booking/{clinic_id}`, the Nuxt assets under `/_nuxt/`, `/favicon.svg` and only these API routes (restrict methods, and clinic UUIDs if possible): `GET /api/v1/online_booking/public/{clinic_id}/config`, `…/logo`, `…/availability`, `…/challenge` and `POST …/requests`, `…/confirm`. Deny everything else, including the staff routes under `/api/v1/online_booking/` and other modules. Trust forwarded client addresses only from that proxy.

Availability also accepts `from_day` and `days` (1–31) on the existing GET endpoint, returning day-grouped slots. Branding is configured through authenticated settings; public copy is treated as plain text and logos are served only from the clinic-scoped logo endpoint. The public request requires a valid phone number, normalized to E.164; the confirmation response supplies the requested time and clinic timezone.

Administrators manage the booking interval, window, minimum notice and an ordered list of bilingual visit reasons. A reason has a stable identifier, duration and active flag; existing reasons must be deactivated rather than deleted to retain request history. Availability accepts an optional `reason` ID and checks the complete duration at each interval. Clinic schedule closures and custom hours are applied through the schedules availability service. The authenticated upload accepts static PNG, JPEG and WebP at most 512 KiB and 1024×1024 pixels. It detects the format from content, checks the filename against it, rejects animation, checks size before base64 decoding and dimensions before pixel loading, and re-encodes a fresh metadata-free PNG. The clinic-scoped public endpoint returns only sanitized PNG with `nosniff`, a sandboxed `default-src 'none'` CSP, ETag and mandatory cache revalidation; it returns 404 for absent images or disabled booking. External logo URLs are not supported. The single migration `ob_0004` adds branding, reasons, logo, quotas, form options, privacy and embed settings and the request columns; it keeps both initial reasons with their configured durations, and downgrade refuses custom-reason requests rather than discarding their identifiers.

Booking quotas are checked while holding the clinic lock and use the clinic local calendar. Quotas, per-contact limits and buffers count only the configured professional: their live holds, accepted requests whose appointment is theirs, and (for buffers) their appointments; other professionals never use up a quota or widen a blocked slot. Hold buffers are snapshotted; optional contact fields are erased with contact data. Redirects, the privacy-policy URL and embed origins require HTTPS.

The public configuration includes the clinic name for accessible branding. Filled controls select a contrast-safe foreground and disabled submission is explained.
